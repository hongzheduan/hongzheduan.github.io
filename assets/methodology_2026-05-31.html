Data & Methodology

BAIZORA  ·  VERSION 2026-06-07  ·  CONFIDENTIAL
01 — Overview

What Baizora Does

Baizora is a daily equity analytics platform covering US large-cap stocks. Each weekday after market close, an automated scanner fetches price, volume, and fundamental data for every ticker in the S&P 500 and Nasdaq-100, computes a standardised set of metrics, and publishes the results to a public JSON feed consumed by the dashboard.

The platform surfaces price momentum, volume activity, and relative valuation signals across seven timeframes — from 1 day to 1 year — allowing users to identify breakouts, trend changes, and sector-relative value at a glance.

02 — Data Universe

Covered Securities

The scanner covers the union of the S&P 500 and Nasdaq-100 constituent lists, deduplicated. As of May 2026 this produces 516 tickers.

03 — Data Sources

Where the Data Comes From

Tiingo (Market Data)

All price and volume data is sourced from Tiingo via a commercial API licence. Tiingo provides end-of-day OHLCV data for US equities with split and dividend adjustments.

  • Bulk daily endpoint — one API call returns the latest EOD bar for all tickers in a single request.
  • Per-ticker history endpoint — fetches up to 2 years of daily OHLCV history on first scan; incremental updates thereafter.
  • Adjusted prices — all OHLCV data is split- and dividend-adjusted.

SEC EDGAR (EPS, Shares, Sector)

Earnings per share, shares outstanding, and SIC sector classification are sourced directly from the SEC EDGAR XBRL API — a free, public API provided by the US Securities and Exchange Commission. No third-party data vendor is used for fundamentals.

  • EPS endpoint: data.sec.gov/api/xbrl/companyfacts/CIK{cik}.json
  • Sector/shares endpoint: data.sec.gov/submissions/CIK{cik}.json
  • XBRL concept: us-gaap/EarningsPerShareDiluted (primary; see EPS section for full field order)
  • All figures are as reported under US GAAP.

Company names are resolved via the EDGAR CIK map (company_tickers.json) as a fallback when the Tiingo meta endpoint is unavailable.

Firebase & Stripe

User authentication is handled by Firebase Auth. Subscription billing uses Stripe. Neither service is involved in market data processing.

04 — Scan Pipeline

Daily Processing Flow

Schedule

The scanner runs as a GitHub Actions workflow on a daily midnight UTC schedule, every day including weekends:

  • Weekdays at 22:00 UTC (6:00 PM ET) — preliminary scan shortly after NYSE close, allowing final trade prints to settle. Commits updated market data.
  • Daily at 00:00 UTC (8:00 PM ET prior day) — final scan with video generation on weekdays. On weekends, carries forward the most recent Friday closing data and refreshes fundamentals if the cache has expired.

Running every night (including weekends) ensures the fundamentals cache is kept warm and the dashboard reflects the latest available data at all times.

Market Closure Detection

On weekdays, before fetching new data, the pipeline probes Tiingo for the current day's SPY data. If the probe returns no results on what should be a trading day, the run aborts and the existing latest.json is left unchanged. This handles unexpected market closures (e.g. the January 2025 Jimmy Carter state funeral holiday).

Regular NYSE holidays are computed algorithmically and skipped without an API probe. Weekend runs bypass the market probe and proceed directly to using cached OHLCV data.

Steps per Run

  1. Update OHLCV cache — one bulk Tiingo API call fetches the latest EOD bar for all 516 tickers; missing history is backfilled per-ticker on first scan.
  2. Load fundamentals — read from disk cache (8-day TTL, committed to git so it persists across runs). Fetch any missing or expired tickers from EDGAR.
  3. Load OHLCV into memory — per-ticker cache files loaded once into a shared dict; each metric computation reads from memory rather than disk.
  4. Compute metrics — for each of 516 tickers: reconstruct price/volume series, calculate all timeframe metrics, fundamentals, scores.
  5. Post-process — compute sector average P/E (market-cap weighted harmonic mean), percentile-rank RSScore and MomentumScore across the full universe.
  6. Data quality check — flag any ticker with >25% 1D price change (likely a cache gap), <200 candle bars, or empty cache files.
  7. Export — write data/latest.json, data/candles.json, and a dated CSV to archive/.
05 — Price & Volume Data

OHLCV Cache

Cache Structure

One JSON file per ticker: data/ohlcv_tiingo_cache/{TICKER}.json. Each file contains the full OHLCV history for that ticker as a list of {date, open, high, low, close, volume} records, sorted ascending by date. Files are updated incrementally — new bars are appended without rewriting history.

The cache holds up to 2 years of daily history (~504 trading days). On first scan a ticker has no cache file and the full history is backfilled from Tiingo. Subsequent scans append only the new bar from the bulk daily endpoint.

Volume Definition

Tiingo's EOD data reports share volume as provided by the exchange feed. Volume figures may include extended-hours trading (pre-market and after-hours sessions) in addition to regular-session activity, depending on the instrument and exchange reporting conventions. Reported volume is therefore systematically higher than platforms that show only regular-session volume. This is not an error — it reflects a broader measure of daily market activity.

06 — Calculated Metrics

Price & Volume Calculations

Timeframe Windows

All multi-day metrics are computed over a fixed number of trading days (not calendar days):

LabelTrading DaysApprox. Calendar
2W102 weeks
1M211 month
3M633 months
6M1266 months
9M1899 months
1Y2521 year

A metric for a given window is only computed if the ticker has at least that many trading days of cache data. If not enough history exists, the field is null.

1D (Single-Day) Metrics

PriceChange1D = (Close[t] − Close[t-1]) / Close[t-1] × 100 (%) VolumeChange1D = (Volume[t] − Volume[t-1]) / Volume[t-1] × 100 (%) PriceVsMA21 = Close[t] / mean(Close[t-20 … t]) VolumeVsMA21 = Volume[t] / mean(Volume[t-20 … t])

PriceVsMA21 and VolumeVsMA21 are ratios (1.0 = exactly at the 21-day moving average). Values above 1.0 indicate the current day is above the recent average.

Live Price & 1D Change (dashboard only)

The authenticated dashboard refreshes the PRICE and 1D P CHG% columns every 60 seconds using Tiingo IEX real-time quotes. The live change is computed as:

1D P CHG% (live) = (IEX_last − scanClose) / scanClose × 100

where scanClose is the prior-night's closing price from latest.json. The IEX prevClose field is deliberately not used because it can be stale or unadjusted on split days.

Stock Split Correction

On forward-split effective dates, Tiingo IEX immediately returns the post-split price while latest.json still holds the pre-split close. Without correction, this causes a large artificial negative 1D change. The dashboard corrects this automatically:

  • data/splits.json is fetched at dashboard load. It contains any forward splits (ratio ≥ 2) from the last 6 months, sourced from the Tiingo /tiingo/daily/{ticker}/splits endpoint and refreshed every nightly scan and every weekend midnight EDGAR run.
  • For each ticker in the split table, the dashboard checks whether the observed ratio scanClose / IEX_last ≈ splitRatio (±20%). If so, it adjusts the reference price to scanClose / splitRatio before computing the change.
  • Once the nightly scanner runs after the split, latest.json is updated to the post-split close and the ratio becomes ≈ 1, so the correction self-disables automatically — no manual intervention required.

Period Metrics (per Timeframe Window)

For each window W (e.g. 3M = last 63 trading days), the following are computed from the slice df.iloc[-W:]:

{W}PriceChange = (Close[-1] − Close[0]) / Close[0] × 100 (start-to-end %) {W}MaxPriceChange = max daily close-to-close return in window × 100 {W}MaxPriceChangeDay = trading days ago the max daily gain occurred {W}MaxVolumeChange = max daily volume change in window × 100 {W}MaxVolumeChangeDay = trading days ago the max volume spike occurred {W}PriceChangeAtMaxVolume = price return on the highest-volume day {W}VolumeChangeAtMaxPrice = volume change on the highest-price-gain day

The "Day" fields count from the end of the window (0 = most recent trading day, 1 = yesterday, etc.).

07 — Fundamental Data

EPS, P/E, Market Cap, Beta & Volatility

Earnings Per Share — TTM Calculation

EPS is trailing twelve months (TTM) diluted GAAP EPS sourced from SEC EDGAR XBRL filings. Diluted EPS is used as the primary field to match the industry-standard methodology used by Yahoo Finance and S&P indices. The following concept fields are tried in order, stopping at the first with data:

  1. EarningsPerShareDiluted (primary)
  2. EarningsPerShareBasic — fallback if diluted unavailable
  3. IncomeLossFromContinuingOperationsPerDilutedShare — required for REITs
  4. IncomeLossFromContinuingOperationsPerBasicShare

YTD Cumulative Filing Detection

Many companies (e.g. Merck, Chevron) file year-to-date cumulative EPS in their 10-Qs rather than single-quarter values. The scanner detects this by comparing the filing's reported period length:

  • Period ≈ 90 days → true quarterly value, used directly.
  • Period ≈ 180 days → H1 YTD; Q2 is derived as H1 − Q1.
  • Period ≈ 270 days → 9M YTD; Q3 is derived as 9M − H1.

Q4 from Annual 10-K

Q4 EPS is never filed in a 10-Q. It is derived as:

Q4 = Annual_10K − 9M_YTD_10Q TTM = Q1_recent + Q2_recent + Q3_recent + Q4_derived

This correctly handles non-December fiscal years (Apple, Nvidia, Costco, etc.) where the most recent annual 10-K covers a different calendar year than the most recent 10-Qs.

The Q3 YTD candidate search uses the full historical 10-Q entry set (no recency cutoff), while the TTM quarterly sum uses only entries within the past two years. This split ensures the Q4 derivation path can always find the correct 9M YTD filing that pairs with an older annual — even for companies whose most recent 10-K pre-dates the two-year rolling window — without exposing the TTM sum to stale quarters from distant fiscal years.

Worked Example: CI (Cigna Group) — TTM vs. One-Time Gains

This example illustrates how the TTM calculation works in practice and why our EPS can legitimately differ from third-party sources like Yahoo Finance.

As of the June 2026 scan, the EDGAR EarningsPerShareDiluted entries for CI under form=10-Q showed:

Q2 2025 (end=2025-06-30, period≈90d): 5.71 (individual quarter) Q3 2025 (end=2025-09-30, period≈90d): 6.98 (individual quarter) Q1 2026 (end=2026-03-31, period≈90d): 6.26 (individual quarter)

Q4 2025 is not in any 10-Q. It was derived from the 10-K:

Q3 YTD (10-Q, start=2025-01-01, end=2025-09-30, period≈273d): ~19.01 FY2025 (10-K, end=2025-12-31): ~23.67 Q4 derived = 23.67 − 19.01 = ~4.66 TTM = 6.26 + 6.98 + 5.71 + 4.66 = 23.61

Yahoo Finance reported trailingEps = 113.71 for the same date, implying a P/E of 2.5× — an implausibly low valuation for a major health insurer. Our P/E of 12.3× is consistent with CI's historical range.

The most likely explanation: Yahoo Finance sourced EPS from the FY2024 10-K, which included a large one-time after-tax gain when Cigna sold its Medicare Advantage and supplemental benefits businesses to Health Care Service Corporation (HCSC). That gain inflated the 2024 reported GAAP EPS well above the company's recurring earnings run rate. By June 2026, our TTM window had rolled entirely past that event, correctly reflecting Cigna's ongoing quarterly earnings of ~$5–7 per share.

Key takeaway: TTM EPS is a rolling window. The same stock can show very different EPS and P/E depending on which four quarters fall inside the window. When a large one-time gain or charge has rolled out of the TTM window, our EDGAR-derived figure will diverge from sources anchored to an older annual 10-K — and our number is typically more representative of the company's recurring earnings power.

Inline XBRL Filing Fallback

A small number of tickers have no EarningsPerShareDiluted data in the EDGAR company_facts API, despite filing regularly with the SEC. For these tickers, the scanner falls back to parsing EPS directly from the inline XBRL embedded in the primary filing document (.htm file).

The fallback applies the same TTM algorithm as the primary path:

  • US domestic filers (10-Q / 10-K) — up to 4 recent 10-Q filings are fetched and parsed; TTM is built from 4 quarterly values with Q4 derived from the annual 10-K where needed. Example: V (Visa) → EPS 11.18, verified against YF 11.48.
  • Foreign IFRS filers (20-F / 40-F) — no quarterly filings exist, so the fallback uses the most recent annual 20-F. Examples: ASML, CCEP, FER, PDD.

Reporting Currency Detection & FX Conversion

Foreign filers report EPS in their home currency (EUR for ASML/CCEP/FER, CNY for PDD). The scanner detects the reporting currency automatically from the unitRef attribute on each inline XBRL tag, which resolves to an ISO 4217 currency code via the filing's unit definitions (e.g. <xbrli:measure>iso4217:EUR</xbrli:measure>).

EPS is then converted to USD using daily ECB reference rates fetched once per scan from the Frankfurter API (free, no API key, updates each business day):

EPS_USD = EPS_local × FX_rate (e.g. ASML: €19.90 × 1.157 = $23.02)

FX rates are cached in memory for the duration of the scan run. If the rate fetch fails, EPS for non-USD filers remains null for that run.

P/E Ratio

PE = Close[t] / EPS_TTM (computed live from current price and cached EPS)

PE is recomputed each scan using the latest price, so it reflects current market valuation even if EPS has not changed since the last fundamentals refresh. PE is set to null if EPS is null, zero, or negative.

Market Capitalisation

MarketCap = SharesOutstanding × Close[t] (recomputed each scan using current price)

Shares outstanding are sourced from SEC EDGAR XBRL via the dei/EntityCommonStockSharesOutstanding concept in the companyfacts API. The following sources are tried in order, requiring a filing date within the past two years:

  1. dei/EntityCommonStockSharesOutstanding — cover-page DEI field; period-end count (primary)
  2. us-gaap/CommonStockSharesOutstanding — balance-sheet equivalent
  3. Inline XBRL parse of the most recent 10-Q or 10-K cover page
  4. us-gaap/WeightedAverageNumberOfSharesOutstandingBasic — TTM average; last resort

Multiplying by the current close price (rather than storing a vendor-supplied market cap figure) ensures the displayed market cap stays fresh on every scan even when the underlying share count has not changed. Third-party cached market cap figures can lag significant buyback activity by weeks or months.

Market cap is published in $billions in latest.json and is used as the weighting factor for the sector average P/E harmonic mean.

Beta

Beta = Cov(stock_returns, SPY_returns) / Var(SPY_returns) — trailing 252 trading days (1 year), daily returns

SPY is fetched fresh each scan via a separate API call (not in the OHLCV cache since SPY is not in the scanner universe). The fetch uses up to 8 retries with exponential backoff to handle rate limiting. If SPY data is still unavailable after all retries, the scanner logs "SPY fetch returned no data — beta will be None" (visible in GitHub Actions run logs) and Beta is null for all tickers that run. Beta is also null if a ticker has fewer than 60 days of history.

30-Day Annualised Volatility

Volatility30D = StdDev(daily_returns[-30:]) × √252

Uses the last 30 trading days of close-to-close returns. Annualised by multiplying by √252.

08 — Sector Classification

How Sectors Are Assigned

Sector assignment follows a two-step priority:

  1. Ticker override table — a hardcoded dict of 26 tickers whose SIC-derived sector is wrong (foreign incorporations, recent index additions, post-reorganisation companies). Takes precedence over all other logic.
  2. SIC-to-sector map — Polygon returns a SIC description string for each company. A static lookup table maps ~150 SIC descriptions to 11 GICS-aligned sectors.

Sector Average P/E — Market-Cap Weighted Harmonic Mean

The sector average P/E is computed as the market-cap weighted harmonic mean of individual P/E ratios within each sector. This is mathematically equivalent to dividing total sector market capitalisation by total implied sector earnings:

SectorAvgPE = Σ(MarketCap_i) / Σ(MarketCap_i / PE_i) = Total Sector Market Cap / Total Implied Earnings

This is the same method used by S&P for their sector indices. It is substantially more robust than a simple arithmetic mean, which is distorted by high-P/E outliers (e.g. a single stock at 600× P/E would dominate a simple average).

PE_vs_Sector is then computed as:

PE_vs_Sector = (PE_i − SectorAvgPE) / SectorAvgPE × 100 (%)
Note on Communication Services: AT&T and Verizon have enormous market caps (~$120–160B each) and low P/E ratios (~10×). Because the sector average is market-cap weighted, these two stocks dominate, pulling the sector average to ~10×. This accurately reflects what a market-cap-weighted index investor experiences in that sector.
09 — Scoring System

Four Composite Scores

Breakout Score (0–100)

Measures immediate price and volume momentum relative to recent averages. Higher = stronger near-term breakout signal.

component_1 = min(33, max(0, (PriceVsMA21 − 1) × 200)) (price above MA21) component_2 = min(33, max(0, PriceChange1D% × 3)) (today's price move) component_3 = min(34, max(0, (VolumeVsMA21 − 1) × 25)) (volume surge) BreakoutScore = round(component_1 + component_2 + component_3)

Volume Pressure Score (−100 to +100)

Combines volume intensity with price direction. Positive = high volume + price up (buying pressure). Negative = high volume + price down (selling pressure).

direction = +1 if PriceChange1D > 0, −1 if < 0, else 0 VolPressureScore = clamp((VolumeVsMA21 − 1) × direction × 100, −100, 100)

Trend Score (0–100)

Fraction of the six timeframes (2W, 1M, 3M, 6M, 9M, 1Y) with positive price change, expressed as a percentage. 100 = uptrend across all timeframes. 0 = downtrend across all. Null timeframes (insufficient history) count as 0.

TrendScore = count(PriceChange > 0 for each window) / 6 × 100

RS Score — Relative Strength (1–99, percentile)

Measures price momentum relative to all other tickers in the universe. Computed as a percentile rank of a weighted raw score across the six timeframes:

RawRS = 0.40×3MPriceChange + 0.20×6MPriceChange + 0.20×9MPriceChange + 0.20×1YPriceChange RSScore = percentile_rank(RawRS, all 516 tickers) × 98 + 1 (scaled to 1–99)

Weights emphasise the 3-month window (the most predictive momentum period in academic literature) while retaining longer-term context.

Momentum Score (0–100, percentile)

Similar to RS Score but weighted toward shorter timeframes, capturing recent acceleration:

RawMomentum = 0.35×1MPriceChange + 0.25×3MPriceChange + 0.20×6MPriceChange + 0.20×1YPriceChange MomentumScore = percentile_rank(RawMomentum, all 516 tickers) × 100
10 — Output Format

Published Data Files

data/latest.json

Primary data file consumed by the dashboard. Published after each successful scan. Top-level structure:

{ "generated_at": "YYYY-MM-DD", "data": [ { ...one object per ticker... } ] }

Each ticker object contains: Ticker, Date, Price, VolumeM, all 1D and period metrics for each timeframe, PE, EPS, MarketCap (in $B), Beta, Volatility30D, Sector, SectorAvgPE, PE_vs_Sector, CompanyName, Spark1Y (normalised close series), and the four scores.

Dashboard — Ticker Modal

Clicking any ticker row opens a modal showing: 1-year candlestick chart, current price with 1D price change (green/red), and a stats grid with P/E, EPS, Volume, Beta, 30D Volatility, Market Cap, Sector, and 1M / 3M / 1Y price change (colour-coded). Modal data is read from the same latest.json row; candle chart data comes from data/candles.json.

Dashboard — Watchlist

Users can star (☆ → ★) any ticker row to save it to a personal watchlist. Saved tickers are persisted in localStorage under the key "baizora_watchlist" and are shared between the EN and CN dashboard versions on the same browser. A dedicated "★ Watchlist" tab filters the main table to show only saved tickers, with all sort, filter, and timeframe controls intact.

data/candles.json

Candlestick data for the modal chart. Loaded separately from latest.json (kept out of the main file to reduce initial page load size).

{ "date": "YYYY-MM-DD", "dates": [ "YYYY-MM-DD", ... ], 252 most recent trading days "data": { "AAPL": [ [open,high,low,close], ... ], ... } }

archive/results_YYYY-MM-DD.csv

A full CSV snapshot of each scan, retained for historical reference. Not consumed by the dashboard.

11 — Known Limitations

Data Gaps & Edge Cases

EPS Not Available (2 Tickers)

ARES and TRI have null EPS. Both filed Form 25-NSE (notification of removal from listing) in May 2026 and are expected to be removed from the S&P 500 / Nasdaq-100 universe on the next index rebalance. All other previously-null tickers (V, CCEP, FER, ASML, PDD, ERIE, KKR, STZ, ARM) now have EPS populated via the inline XBRL filing fallback — see the Inline XBRL Fallback section above.

Short OHLCV History

BNY (Bank of New York Mellon, ticker changed from BK in 2025), BF-B, BRK-B, FISV, and Q have fewer than 252 clean trading days in the cache. Longer-period metrics (9M, 1Y) are null for these tickers and will fill in as the cache accumulates daily data going forward.

Stock Split Adjustments

Polygon returns split-adjusted prices automatically. EDGAR EPS filings are not retroactively adjusted until the company files its next 10-Q or 10-K on a post-split share basis. For BKNG (25-for-1 split, April 2026), the scanner manually divides EDGAR EPS by 25 until the Q2 2026 10-Q is filed (expected August 2026), at which point EDGAR will self-correct and the guard condition will disable automatically.

Fundamentals Cache TTL

Company fundamentals (EPS, sector, shares outstanding) are cached with an 8-day TTL. The cache file is committed to the repository and persists across daily scanner runs, so EDGAR is only re-fetched when the cache expires. P/E ratios may therefore reflect EPS up to 8 days old. In practice this introduces negligible error, since EDGAR XBRL data only changes when a company files a new 10-Q or 10-K (quarterly cadence).

Candle Chart History

The candles.json date window covers the most recent 252 trading days. For tickers with fewer clean OHLCV entries in that window, the chart will show fewer candles and the x-axis labels will correspond to the tail of the 252-day window.

Sector Average P/E Universe

Sector average P/E is computed only from tickers within the Baizora universe (S&P 500 + Nasdaq-100). This skews sector averages upward relative to the full market — the universe is dominated by large-cap and growth companies. The market-cap weighted harmonic mean mitigates this by anchoring the average to the largest companies' valuations, which approximate the sector index experience.

Scalability

GitHub Pages is served via Fastly CDN with no concurrent user limit for static files. The soft bandwidth limit is 100 GB/month — at ~5 MB per latest.json load, that supports roughly 20,000 full page loads per month. Repeat visitors do not re-download HTML/CSS/JS (browser-cached), so the effective limit is much higher in practice. GitHub does not charge for Pages bandwidth.

Google Cloud Functions free tier covers 2,000,000 invocations/month. The /api/iex-quotes endpoint uses a 60-second in-memory cache — regardless of how many users are on the homepage simultaneously, the function is invoked at most once per minute (~31,680 calls/month), well within the free tier. EDGAR and Tiingo are only called by GitHub Actions (nightly batch) and are entirely decoupled from user traffic.

Firebase Auth is free up to 50,000 monthly active users on the Blaze plan.

Cost at Scale

At 1,000 daily active users:

  • GitHub Pages: $0
  • Google Cloud Functions: $0 (well within free tier)
  • Firebase Auth: $0
  • Total infrastructure: ~$1–2/month (unchanged from current)
  • Stripe fees: ~$32/month if 10% convert to paid (~100 subscribers × $9.99)
  • Net revenue at 10% conversion: ~$967/month

When Architecture Would Need to Change

  • Real-time sub-second price streaming — would require a WebSocket service. Current 60-second polling is intentional and sufficient for the product.
  • Sustained traffic exceeding 100 GB/month on GitHub Pages — mitigation is simple: gzip latest.json server-side (~10× size reduction to ~500 KB).
