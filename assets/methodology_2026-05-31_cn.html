01 — 概述

贝佐拉是什么

贝佐拉是一个覆盖美国大盘股的每日股票量价分析平台。每个交易日收盘后,自动化扫描程序会为标普500和纳斯达克100指数中的每一只股票抓取价格、成交量和基本面数据,计算一套标准化的指标,并将结果发布为公开的 JSON 数据源,供仪表盘调用。

平台在1天到1年共七个时间窗口中呈现价格动量、成交量活跃度和相对估值信号,帮助用户一目了然地识别突破、趋势变化和行业相对价值。

02 — 数据范围

覆盖的证券

扫描程序覆盖标普500和纳斯达克100成分股列表的并集(已去重)。截至2026年7月,共计516只股票。这一数字会随指数成分变动而变化——参见指数成分变动。

指数大致数量说明
标普500502按流通市值计算的美国最大公司
纳斯达克100101纳斯达克上市的100家最大非金融公司
并集(去重)516属于任一或两个指数的股票

所有证券均为美股上市的普通股(包括部分在美上市的外国注册公司,如 ASML、BKNG、CCEP、NBIS)。扫描程序不覆盖 ETF、优先股、认股权证或固定收益产品。

指数成分变动

每次扫描运行开始时,都会从 Slickcharts(slickcharts.com/sp500、slickcharts.com/nasdaq100)重新抓取成分股列表。任何权重为 0% 的条目都会被视为过期/已摘牌的残留列表项并被剔除——Slickcharts 有时会在指数实际变动后数天仍保留已离场成分股的条目(曾观察到 EchoStar/SATS 的案例:该公司已于 2026-06-24 将股票代码改为 ECHO 并退出标普500,但一周后 Slickcharts 上仍显示其 0.00% 权重的条目)。

新增和移除是通过与扫描程序自身此前保存的股票列表做差异比对得出的(而非每次都与 Slickcharts 的原始表格比对),因此一只已离场的股票只会被记录为"移除"一次——即便 Slickcharts 一直保留其残留条目也不会重复记录。变动会被写入 data/index_changes.json,并在仪表盘的"成分变动"标签页中展示。

03 — 数据来源

数据从何而来

Tiingo(市场数据)

所有价格和成交量数据均通过商业 API 授权从 Tiingo 获取。Tiingo 为美股提供经过拆股和分红调整的日线 OHLCV 数据。

  • 批量日线接口 — 一次 API 调用即可返回全部股票的最新收盘数据。
  • 单只股票历史接口 — 首次扫描时获取最长2年的日线历史;此后为增量更新。
  • 调整后价格 — 所有 OHLCV 数据均已做拆股与分红调整。

美国证监会 EDGAR(每股收益、股本、行业)

每股收益、流通股本以及 SIC 行业分类均直接来自 SEC EDGAR XBRL API——由美国证券交易委员会提供的免费公开 API。基本面数据不依赖任何第三方数据商。

  • EPS 接口:data.sec.gov/api/xbrl/companyfacts/CIK{cik}.json
  • 行业/股本接口:data.sec.gov/submissions/CIK{cik}.json
  • XBRL 概念:us-gaap/EarningsPerShareDiluted(主要字段;完整字段优先级见 EPS 章节)
  • 所有数据均按美国通用会计准则(US GAAP)口径披露。

当 Tiingo 的元数据接口不可用时,公司名称会通过 EDGAR CIK 映射表(company_tickers.json)作为备用方案解析。

Firebase 与 Stripe

用户身份验证由 Firebase Auth 处理。订阅计费使用 Stripe。两者均不参与市场数据处理。

04 — 扫描流程

每日处理流程

运行时间表

扫描程序以 GitHub Actions 工作流的形式运行,工作日按五个时段执行(均为美东时间;因 CI 排队延迟,实际执行时间通常比计划时间晚1-2小时):

计划时间用途EDGAR 重新抓取
下午4:30主要收盘扫描 + 视频生成完整重新抓取
下午5:00重试——若4:30已完整更新则整体跳过使用缓存
下午5:30重试——无论前几轮结果如何都会执行使用缓存
下午6:30重试——无论前几轮结果如何都会执行使用缓存
晚上11:00兜底运行——使用当前可获取的任何数据强制执行完整重新抓取

周六和周日,还会额外执行一次约凌晨1点(美东时间)的运行,仅刷新 SEC EDGAR 基本面数据(不进行市场扫描),确保休市期间基本面缓存依然保持最新。

工作日设置多个重试时段的原因是:Tiingo 并不总能同时为全部股票发布完整的收盘数据——详见下方数据完整性保护机制。

休市检测

在抓取新数据之前,程序会先探测 Tiingo 当天的 SPY 数据是否就绪。如果未能确认当日数据,会每隔30分钟重试一次(重试次数因时段而异),若始终无法确认则放弃本轮运行,保持 latest.json 不变。该机制既能应对常规的数据发布延迟,也能应对突发性休市(如2025年1月因吉米·卡特国葬导致的休市)。

常规的纽交所假期通过算法自动计算并跳过,无需 API 探测。晚上11点的兜底运行以及手动触发的运行会完全绕过假期检测和数据就绪探测,直接使用当前可获取的数据。

每次运行的步骤

  1. 更新指数成分 — 重新抓取标普500/纳斯达克100成分股列表,过滤掉权重为0%的条目,检测并记录新增/移除的股票。
  2. 更新 OHLCV 缓存 — 一次批量 Tiingo API 调用获取全部股票的最新收盘数据;首次扫描时对缺失的历史数据进行补全。
  3. 加载基本面数据 — 启用 EDGAR 的运行会始终为每只股票重新抓取最新数据(无基本面缓存有效期——见基本面数据新鲜度);仅使用缓存的运行则读取最近一次启用 EDGAR 的运行所提交的基本面数据。
  4. 将 OHLCV 加载到内存 — 各股票的缓存文件仅加载一次到共享字典中;每个指标计算均从内存而非磁盘读取。
  5. 计算指标 — 对范围内的每一只股票:重建价格/成交量序列,计算所有时间窗口的指标、基本面数据和评分。
  6. 剔除过期股票 — 在发布之前,剔除所抓取数据日期与已确认的市场日期不一致的股票(详见下文)。
  7. 后处理 — 计算行业平均市盈率(按市值加权的调和平均数),在全部股票范围内计算 RSScore 和 MomentumScore 的百分位排名。
  8. 数据质量检查 — 标记单日价格变动超过25%(可能是缓存缺口)、K线少于200根,或缓存文件为空的股票。
  9. 导出 — 写入 data/latest.json、data/candles.json,以及一份带日期的 CSV 存档到 archive/。
04b — 数据完整性

数据完整性保护机制

Tiingo 并不总是在同一时刻为范围内的每只股票都发布完整的收盘数据——有些股票可能比其他股票延迟数分钟到数小时,偶尔更久。以下两项保护机制用于防止这种情况导致输出错误或标注误导性的数据。

逐股票的过期数据剔除

上文提到的市场就绪探测仅确认 SPY 本身拥有当日数据——并不能保证其他每只股票也是如此。每次扫描计算出结果后,系统会将每只股票所抓取的数据日期与已确认的市场日期进行比对。只要出现任何不一致——哪怕仅相差一天——该股票就会被整体排除在本轮输出之外,而不是让它带着"看起来是当日数据"的标签发布过期的价格/成交量。

发布的 data/latest.json 中会携带两个反映该机制的额外字段:

partialUpdate: true | false // 若本轮有任何股票被剔除,则为 true staleTickers: ["股票代码", ...] // 被剔除的具体股票(如有)

当 partialUpdate 为 true 时,仪表盘顶部会显示一条琥珀色提示(仅显示数量,不列出具体股票名——如果同时有大量股票受影响,列出全部名称会撑爆提示条),说明数据通常会在约30分钟内更新,但不会承诺确切时间。一旦后续运行(无论是定时还是手动触发)获取到该股票的最新数据,它会自动重新出现——无需任何特殊的恢复操作。

重试效率优化

如果下午4:30的运行已经实现了完整更新(partialUpdate: false),下午5:00的重试时段会直接跳过本轮扫描——既然没有需要补漏的内容,重新扫描一遍全部股票只会得到完全相同的结果。下午5:30和6:30的时段则始终无条件执行,作为当晚后续时间里针对任何仍未解决问题的兜底保障。

05 — 价格与成交量数据

OHLCV 缓存

缓存结构

每只股票对应一个 JSON 文件:data/ohlcv_tiingo_cache/{股票代码}.json。每个文件包含该股票完整的 OHLCV 历史记录,以 {date, open, high, low, close, volume} 记录列表形式按日期升序排列。文件采用增量更新——新的数据只会被追加,不会重写历史记录。

缓存保留最长2年的日线历史(约504个交易日)。首次扫描某只股票时,尚无缓存文件,会从 Tiingo 补全完整历史。后续扫描仅从批量日线接口追加最新一根K线。

成交量定义

Tiingo 的收盘数据按交易所数据源提供的口径报告股票成交量。根据具体证券和交易所的披露惯例,成交量数字可能包含盘前和盘后的场外交易量,而不仅仅是常规交易时段的成交量。因此,报告的成交量通常系统性地高于只显示常规交易时段成交量的平台。这并非错误——它反映的是更广义的每日市场活跃度。

06 — 计算指标

价格与成交量计算方法

时间窗口

所有多日指标均按固定数量的交易日(而非自然日)计算:

标签交易日数大致对应自然天数
2周102周
1月211个月
3月633个月
6月1266个月
9月1899个月
1年2521年

只有当某只股票拥有至少对应数量的交易日缓存数据时,该窗口的指标才会被计算。若历史数据不足,该字段为 null。

单日指标

PriceChange1D = (Close[t] − Close[t-1]) / Close[t-1] × 100 (百分比) VolumeChange1D = (Volume[t] − Volume[t-1]) / Volume[t-1] × 100 (百分比) PriceVsMA21 = Close[t] / mean(Close[t-20 … t]) VolumeVsMA21 = Volume[t] / mean(Volume[t-20 … t])

PriceVsMA21 和 VolumeVsMA21 均为比值(1.0 表示恰好等于21日均值)。大于1.0表示当日数值高于近期均值。

实时价格与单日涨跌幅(仅限仪表盘)

已登录仪表盘使用 Tiingo IEX 实时报价,每 10秒刷新一次价格和日涨跌幅两列,生效时段为工作日美东时间上午9:30至晚上8:00(isMarketOpen()——刻意延伸至下午4:00收盘之后,以便在当晚下午4:00至6:30这段扫描结果尚未落地的空档期内,继续显示实时价格)。实时涨跌幅计算公式为:

日涨跌幅(实时) = (IEX_last − scanClose) / scanClose × 100

其中 scanClose 为 latest.json 中记录的前一晚收盘价。IEX 的 prevClose 字段被刻意弃用,因为它在拆股当天可能过期或未经调整。

一旦新一轮扫描结果落地、页面自动刷新后(每5分钟轮询一次),scanClose 本身就会变成当天的收盘价——此时仪表盘会在剩余的8点时段内停止叠加 IEX 实时数据(否则用当天收盘价与自身比较会导致所有单日涨跌幅显示为0%),转而显示扫描程序自身计算出的 PriceChange1D。

拆股修正

在正向拆股生效当天,Tiingo IEX 会立即返回拆股后的价格,而 latest.json 中仍保留拆股前的收盘价。若不加修正,会导致出现巨大的虚假单日跌幅。仪表盘会自动修正该问题:

  • 仪表盘加载时会获取 data/splits.json,其中包含过去6个月内比例≥2的正向拆股信息,数据源自 Tiingo 的 /tiingo/daily/{ticker}/splits 接口,并在每次夜间扫描和每个周末凌晨的 EDGAR 运行中刷新。
  • 对于拆股表中的每只股票,仪表盘会检查观测到的比例 scanClose / IEX_last ≈ splitRatio(±20%)是否成立。若成立,则在计算涨跌幅之前,将参考价格调整为 scanClose / splitRatio。
  • 一旦拆股后的夜间扫描运行,latest.json 会更新为拆股后的收盘价,比例趋近于1,该修正机制便会自动失效——无需人工干预。

区间指标(按时间窗口)

对于每个窗口 W(例如3月 = 最近63个交易日),以下指标均从切片 df.iloc[-W:] 中计算得出:

{W}PriceChange = (Close[-1] − Close[0]) / Close[0] × 100 (区间首尾涨跌幅) {W}MaxPriceChange = 区间内单日最大涨跌幅 × 100 {W}MaxPriceChangeDay = 单日最大涨幅发生在几个交易日之前 {W}MaxVolumeChange = 区间内单日最大成交量变化 × 100 {W}MaxVolumeChangeDay = 单日最大成交量激增发生在几个交易日之前 {W}PriceChangeAtMaxVolume = 成交量最高当日的价格涨跌幅 {W}VolumeChangeAtMaxPrice = 价格涨幅最大当日的成交量变化

"天数"字段均从窗口的末端开始计数(0 = 最近一个交易日,1 = 前一交易日,以此类推)。

07 — 基本面数据

每股收益、市盈率、市值、贝塔系数与波动率

每股收益 — TTM 计算方法

EPS 采用过去十二个月(TTM)摊薄后的 GAAP 每股收益,数据来自 SEC EDGAR XBRL 文件。之所以以摊薄每股收益作为主要字段,是为了与雅虎财经和标普指数所采用的行业标准方法保持一致。以下概念字段按顺序依次尝试,遇到第一个有数据的字段即停止:

  1. EarningsPerShareDiluted (主要字段)
  2. EarningsPerShareBasic — 若摊薄数据不可用时的备用字段
  3. IncomeLossFromContinuingOperationsPerDilutedShare — REIT 必需字段
  4. IncomeLossFromContinuingOperationsPerBasicShare

年初至今累计披露的识别

许多公司(如默克、雪佛龙)在10-Q中披露的是年初至今累计EPS,而非单季度数值。扫描程序通过比较披露期间的长度来识别这种情况:

  • 期间约90天 → 真实单季度数值,直接使用。
  • 期间约180天 → 上半年累计;第二季度 = 上半年 − 第一季度。
  • 期间约270天 → 前三季度累计;第三季度 = 前三季度累计 − 上半年。

从年度10-K推导第四季度数据

第四季度EPS从不会单独出现在10-Q中,需通过以下方式推导:

第四季度 = 年度10-K − 前三季度累计(10-Q) TTM = 最近第一季度 + 最近第二季度 + 最近第三季度 + 推导出的第四季度

该方法能正确处理财年结束月份非12月的公司(如苹果、英伟达、好市多等),此时最新的年度10-K所覆盖的自然年度与最新几份10-Q并不相同。

用于查找"前三季度累计"匹配项的搜索会使用完整的历史10-Q记录(不设时效限制),而TTM季度求和则只使用过去两年内的记录。这种区分确保了即便某公司最新的10-K已超出两年滚动窗口,第四季度推导路径也总能找到与之匹配的正确的"前三季度累计"披露记录——同时又不会让TTM求和暴露在遥远财年的过期季度数据风险之下。

实例分析:CI(信诺集团)— TTM 与一次性收益的关系

本例说明了TTM计算在实践中的运作方式,以及我们的EPS为何可能与雅虎财经等第三方数据源出现合理的差异。

截至2026年6月的扫描,EDGAR 中 CI 在 form=10-Q 下的 EarningsPerShareDiluted 记录如下:

2025年第二季度 (截至=2025-06-30,期间≈90天): 5.71 (单季度数值) 2025年第三季度 (截至=2025-09-30,期间≈90天): 6.98 (单季度数值) 2026年第一季度 (截至=2026-03-31,期间≈90天): 6.26 (单季度数值)

2025年第四季度不在任何10-Q中,是从10-K推导得出的:

前三季度累计 (10-Q,起始=2025-01-01,截至=2025-09-30,期间≈273天): ~19.01 2025财年 (10-K,截至=2025-12-31): ~23.67 推导出的第四季度 = 23.67 − 19.01 = ~4.66 TTM = 6.26 + 6.98 + 5.71 + 4.66 = 23.61

同期雅虎财经披露的 trailingEps = 113.71,对应市盈率仅2.5倍——对一家大型健康险公司而言,这样的估值低得难以置信。而我们计算出的12.3倍市盈率与CI的历史区间相符。

最可能的解释是:雅虎财经的EPS数据来源于2024财年10-K,其中包含信诺出售其"联邦医疗保险优势计划"及补充福利业务给美国医疗服务公司(HCSC)所产生的一笔巨额一次性税后收益。这笔收益大幅拉高了2024年披露的GAAP每股收益,远超公司经常性盈利水平。到2026年6月,我们的TTM窗口已经完全滚动越过了这一事件,正确反映了信诺约每股5-7美元的常态季度盈利水平。

关键要点:TTM每股收益是一个滚动窗口。同一只股票在不同的四个季度组合下,EPS和市盈率可能大相径庭。当一笔巨额一次性收益或支出滚出TTM窗口后,我们基于EDGAR推导出的数值就会与那些锚定在较旧年度10-K上的数据源产生分歧——而我们的数字通常更能代表该公司的经常性盈利能力。

内嵌 XBRL 文件备用方案

少数股票尽管定期向SEC披露文件,但其EDGAR company_facts API 中并没有 EarningsPerShareDiluted 系列数据。对于这些股票,扫描程序会退而求其次,直接从主披露文件(.htm)中内嵌的XBRL数据解析EPS。截至2026年7月,共有11只股票适用此方案:KKR、BRK-B、V、ERIE、STZ、HSY(美国境内披露方)以及 ARM、ASML、CCEP、FER、PDD、NBIS(境外披露方)。这份名单并非固定不变——会随着 company_facts 数据老化或披露方调整标记方式而变化,因此每次都从实时EDGAR数据重新判定,而非硬编码。

该备用方案沿用与主路径相同的TTM构建优先级——关键在于,第四季度推导路径(前三季度 + 年度 − 前三季度累计)始终优先于"直接汇总任意可获得的4个季度日期"这种简单粗暴的兜底方式。第四季度从不会单独以10-Q形式披露(它被并入了10-K),因此简单汇总方式一旦执行,就会悄悄用一个过期的去年同期季度数据替代真实的第四季度——这一问题在2026年7月被发现并针对六只股票修复(修复前,KKR的TTM每股收益被低估了约2倍)。

  • 美国境内披露方(10-Q / 10-K) — 获取并解析最近最多4份10-Q;每当自上一份年度报告以来披露的真实季度数不足4个(这是常见情况)时,第四季度就会从年度10-K中推导得出。
  • 境外披露方(20-F / 40-F / 6-K) — 这些公司不存在季度披露,因此备用方案直接使用最近一份年度数据。例如:ASML、CCEP、FER、PDD(20-F),NBIS(6-K,由外国私人发行人提交)。

披露币种识别与汇率换算

境外披露方以其本国货币披露EPS(ASML/CCEP/FER为欧元,PDD为人民币)。扫描程序会自动从每个内嵌XBRL标签的 unitRef 属性中识别披露币种,该属性通过文件的单位定义解析为 ISO 4217 货币代码(例如 <xbrli:measure>iso4217:EUR</xbrli:measure>)。

随后,EPS会使用每次扫描获取一次的欧洲央行(ECB)每日参考汇率(来自免费、无需API密钥、每个交易日更新的 Frankfurter API)换算为美元:

EPS_美元 = EPS_本币 × 汇率

汇率会在扫描运行期间缓存于内存中。若汇率获取失败,当次运行中非美元披露方的EPS将保持为空。

市盈率(P/E)

市盈率 = Close[t] / EPS_TTM (每次扫描时用当前价格与缓存的EPS实时计算)

市盈率每次扫描都会用最新价格重新计算,因此即便自上次基本面刷新以来EPS未变化,市盈率仍能反映当前市场估值。若EPS为空、为零或为负,市盈率将设为 null。

市值

市值 = 流通股本 × Close[t] (每次扫描时用当前价格重新计算)

流通股本数据来自 SEC EDGAR XBRL,通过 companyfacts API 中的 dei/EntityCommonStockSharesOutstanding 概念获取。以下数据源按顺序依次尝试,均要求披露日期在过去两年以内:

  1. dei/EntityCommonStockSharesOutstanding — 封面页DEI字段;期末数量 (主要来源)
  2. us-gaap/CommonStockSharesOutstanding — 资产负债表对应字段
  3. 解析最近一份10-Q或10-K封面页中的内嵌XBRL数据
  4. us-gaap/WeightedAverageNumberOfSharesOutstandingBasic — TTM平均值;最后的备选方案

使用当前收盘价相乘(而非存储数据商提供的市值数字),确保即便股本未发生变化,展示的市值也能在每次扫描中保持最新。第三方缓存的市值数字可能滞后于重大回购活动数周甚至数月。

贝塔系数

贝塔系数 = Cov(个股收益率, SPY收益率) / Var(SPY收益率) — 过去252个交易日(1年)的日收益率

SPY数据每次扫描都会通过单独的API调用重新获取(不在OHLCV缓存中,因为SPY本身不属于扫描范围)。该请求最多重试8次并采用指数退避策略以应对限流。若重试全部失败后仍无法获取SPY数据,程序会记录"SPY fetch returned no data — beta will be None"日志(可在GitHub Actions运行日志中查看),当次运行所有股票的贝塔系数均为空。若某只股票历史数据不足60天,其贝塔系数同样为空。

30日年化波动率

30日波动率 = StdDev(最近30日收益率) × √252

使用最近30个交易日的收盘价对收盘价收益率计算,乘以√252进行年化处理。

08 — 行业分类

行业如何被分配

行业分配遵循两级优先顺序:

  1. 股票代码覆盖表 — 一个包含46只股票的硬编码字典,这些股票由SIC推导出的行业存在偏差(外国注册、近期新纳入指数、重组后公司等原因)。该表优先级高于其他所有逻辑。
  2. SIC对行业映射表 — SEC EDGAR 通过其 submissions API 为每家公司返回SIC(标准行业分类)描述字符串。一张静态查找表将256种SIC描述(加上针对未收录情况的关键词模糊匹配)映射到11个与GICS对齐的行业。

行业平均市盈率 — 市值加权调和平均数

行业平均市盈率按各行业内个股市盈率的市值加权调和平均数计算,数学上等价于用行业总市值除以行业隐含总盈利:

行业平均市盈率 = Σ(市值_i) / Σ(市值_i / 市盈率_i) = 行业总市值 / 行业隐含总盈利

这与标普用于其行业指数的方法相同。相比简单算术平均数,该方法要稳健得多——简单平均容易被高市盈率的异常值扭曲(例如单一一只600倍市盈率的股票就足以主导简单平均结果)。

相对行业市盈率(PE_vs_Sector)计算方式为:

相对行业市盈率 = (市盈率_i − 行业平均市盈率) / 行业平均市盈率 × 100 (百分比)
关于通信服务行业的说明:AT&T和Verizon市值巨大(各约1200-1600亿美元),市盈率较低(约10倍)。由于行业平均值按市值加权,这两只股票占据主导地位,将行业平均值拉低至约10倍。这准确反映了按市值加权的指数投资者在该行业中的实际体验。
09 — 评分体系

四项综合评分

突破评分(0–100)

衡量相对于近期均值的即时价格和成交量动量。数值越高代表短期突破信号越强。

分量1 = min(33, max(0, (PriceVsMA21 − 1) × 200)) (价格高于MA21均线) 分量2 = min(33, max(0, 日涨跌幅% × 3)) (当日价格波动) 分量3 = min(34, max(0, (VolumeVsMA21 − 1) × 25)) (成交量放大) 突破评分 = round(分量1 + 分量2 + 分量3)

量能压力评分(−100 至 +100)

综合成交量强度与价格方向。正值 = 放量上涨(买盘压力);负值 = 放量下跌(卖盘压力)。

方向 = +1(若日涨跌幅 > 0)、−1(若 < 0)、否则为 0 量能压力评分 = clamp((VolumeVsMA21 − 1) × 方向 × 100, −100, 100)

趋势评分(0–100)

六个时间窗口(2周、1月、3月、6月、9月、1年)中价格上涨的窗口占比,以百分比表示。100 = 全部窗口均上涨;0 = 全部窗口均下跌。历史数据不足导致为空的窗口按0计算。

趋势评分 = count(各窗口涨跌幅 > 0 的数量) / 6 × 100

相对强度评分(1–99,百分位)

衡量相对于范围内所有其他股票的价格动量。基于六个时间窗口的加权原始得分计算出百分位排名:

原始RS得分 = 0.40×3月涨跌幅 + 0.20×6月涨跌幅 + 0.20×9月涨跌幅 + 0.20×1年涨跌幅 相对强度评分 = percentile_rank(原始RS得分, 全部516只股票) × 98 + 1 (缩放至1–99)

权重侧重于3个月窗口(学术文献中最具预测力的动量周期),同时保留长期背景信息。

动量评分(0–100,百分位)

与相对强度评分类似,但更侧重短期窗口,用于捕捉近期加速迹象:

原始动量得分 = 0.35×1月涨跌幅 + 0.25×3月涨跌幅 + 0.20×6月涨跌幅 + 0.20×1年涨跌幅 动量评分 = percentile_rank(原始动量得分, 全部516只股票) × 100

11 — 已知局限性

数据缺口与边界情况

EPS 数据不可用(3只股票)

ARES 和 TRI 的EPS为空——两者均于2026年5月提交了25-NSE表格(摘牌通知)。FDXF(联邦快递货运分拆公司,2026年6月)EPS为空,单纯是因为尚未披露10-Q或10-K——目前只有一份8-K和几份Form 4。所有其他缺乏主路径company_facts EPS数据的股票,均通过内嵌XBRL备用方案获取数据——参见上文内嵌XBRL备用方案。

OHLCV 历史数据较短

近期上市或近期分拆的股票在缓存中的干净交易日不足252天——截至2026年7月,这包括 FDXF(约24天)、Q(约165天)和 PSKY(派拉蒙天空之舞,约227天)。在缓存积累足够的日线历史之前,这些股票的长周期指标(9月、1年)均为空。

拆股调整

Tiingo会自动对历史K线追溯性地返回拆股调整后的价格。EDGAR的EPS和流通股本披露不会追溯调整——只有当公司披露下一份10-Q或10-K后,才会反映拆股后的股本数量。这会产生一个临时缺口(Tiingo已显示拆股后价格,而EDGAR仍显示拆股前的EPS/股本),由上文"特殊情况"中所述的条件触发式拆股防护逻辑自动弥合。

基本面数据新鲜度

公司基本面数据(EPS、行业、流通股本)不设缓存有效期——每次启用EDGAR的扫描运行(工作日下午4:30和晚上11点,以及周末的EDGAR专用运行)都会为每只股票重新从SEC EDGAR抓取最新数据,而非复用过期的本地缓存。下午5:00/5:30/6:30的重试时段则会复用最近一次启用EDGAR的运行所提交的基本面数据,而非重新抓取,因为EDGAR披露文件不会在日内发生变化。这意味着只要公司已经披露,市盈率就能反映当日的EPS,而不会因固定的缓存周期而滞后。

K线图历史长度

candles.json 的日期窗口覆盖最近252个交易日。对于该窗口内干净OHLCV记录较少的股票,图表显示的K线会相应减少,横轴标签也会对应252天窗口的尾部区间。

行业平均市盈率的计算范围

行业平均市盈率仅基于贝佐拉覆盖范围内(标普500 + 纳斯达克100)的股票计算。这会使行业平均值相对整体市场偏高——该范围以大盘股和成长股为主。市值加权调和平均法通过将平均值锚定在最大市值公司的估值上来缓解这一问题,从而近似反映行业指数投资者的实际体验。

可扩展性

GitHub Pages 通过 Fastly CDN 提供服务,静态文件无并发用户数限制。软性带宽限制为每月100GB——按每次 latest.json 加载约5MB计算,可支撑每月约2万次完整页面加载。回访用户无需重新下载HTML/CSS/JS(浏览器已缓存),因此实际有效上限更高。GitHub不对Pages带宽收费。

Google Cloud Functions 免费额度覆盖每月200万次调用。/api/iex-quotes 接口采用60秒内存缓存——无论首页同时在线用户数多少,该函数每分钟最多被调用一次(约每月31,680次),远低于免费额度上限。EDGAR和Tiingo仅由GitHub Actions(夜间批处理)调用,与用户流量完全解耦。

Firebase Auth 在Blaze方案下月活5万用户以内免费。

规模化成本

按每日1,000名活跃用户计算:

  • GitHub Pages:0美元
  • Google Cloud Functions:0美元(远低于免费额度)
  • Firebase Auth:0美元
  • 基础设施总成本:约每月1-2美元(与当前一致)
  • Stripe手续费:若10%转化为付费用户(约100名订阅者 × 9.99美元),约每月32美元
  • 10%转化率下的净收入:约每月967美元

何时需要调整架构

  • 亚秒级实时价格推送 — 需要WebSocket服务。目前60秒轮询的方案是有意为之,已满足产品需求。
  • 持续超过每月100GB的流量(GitHub Pages)— 应对方式很简单:在服务端对 latest.json 做gzip压缩(体积可缩小约10倍,降至约500KB)。

就目前规模而言,以上两种情况均不构成实际风险。
